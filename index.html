把业务，翻译成在跑的系统。

以 FDE（Forward Deployed Engineer，前线部署工程师）的方式做企业 AI 落地：驻场进客户的群、数据和流程里，亲自写代码，交付在业务里跑起来的系统，而不是报告和 PPT。麦肯锡的调研里，88% 的企业已经在用 AI，但约三分之二还停在零散试点——差距不在工具，在运营方式。我做的，是把 AI 原生企业的运营准则翻译进传统企业。

五步工作法

  1. 跟岗观察：看员工每天忙什么、卡在哪、重复什么 → 现场观察记录
  2. 痛点定位：只挑同时「繁琐、高频、易错」的环节 → 痛点清单 + 成功标准
  3. 流程拆解：每一步的输入、输出、异常都写清楚 → 流程图 + 数据字典
  4. 翻译封装：写成规则、脚本和 Agent 动作链，开发成系统 → 可运行系统 + 测试
  5. 赋能输出：先带会 3–5 名种子用户，再由他们带团队 → 手册 + 教学视频

先划清谁做什么，AI 才敢进核心业务

确定性自动化（脚本与规则引擎：搬运、匹配、计算、留痕）→ AI 辅助（识别、归类、起草，只出候选）→ 人工判断（风险判断、最终结论，永远不自动化）。AI 的自主度按 L0–L3 分级，平行运行达标才升一级，出错即降级。

六个案例

每个案例都按同一个闭环推进：现场诊断 → 最小可用 → 平行运行验收 → 带教交付 → 沉淀成积木 → 用到下一个客户。从一个痛点（点）切进去，串起上下游（线），最后覆盖整个业务域（面）。进度如实标注：已交付 · 进行中 · 搭建中 · 诊断中 · 原型。点开看每个案例的约束、判断、架构和验收方式。

A曼谷某审计事务所：零 AI 约束下，把实质性程序打通成一条线进行中

背景与约束

风险导向审计要求审计师把时间花在风险判断和异常调查上，但现场时间被导数、粘贴、填底稿占满。事务所的治理还没放行 AI，硬约束有四条：零 AI、数据不出本机、中英泰三语界面、单文件离线运行，并且要对齐 ISA 315 / 330 / 230 / 220。

我的判断

在 AI 被放行之前，先用确定性规则把实质性程序打通成一条线，AI 是之后的候选层，而不是起点。我把核心问题“如何把审计师的时间还给风险判断”拆成五个互不重叠的模块：数据准备更快、异常发现更准、底稿编制更省、结果经得起复核、AI 接入可控。每个模块对应工作台里一个可验收的部分。

方案架构（工作台 v0.2，生产使用中）

  1. 数据提取：CSV 导入 + 字段别名映射，不做 OCR
  2. 质量闸门：结构、完整、唯一性检查，TB–GL–子账勾稽，不过关就拦截，不进规则引擎
  3. 规则引擎：四条规则，阈值可调，命中结果按 B / C / D 分层，高风险先调查
  4. 底稿生成：数字自动填充，“解释 → 证据 → 评价 → 结论”四栏人工调查，结论栏只能由人填
  5. 任务看板：P1–P6 风险导向审计六阶段、18 项任务，状态存本机

边界情况单独设计：上期为零、金额为负、科目缺失、零命中、波动超过 500%。新增规则先填“模块设计卡”：目的、认定、输入、规则、输出、人工干预点、测试用例。每次运行生成 Run ID 和参数快照，可一键导出五文件运行包，满足 ISA 230 底稿和 ISA 220 质量管理的可追溯要求。全部计算在浏览器内存里完成，零网络请求。

怎么验收

“看起来合理”不算验收，逐项对账才算。新旧流程平行运行，对比总行数、总金额、异常数、人工发现但自动遗漏的异常、自动化新发现的异常、底稿完成用时。上线门槛：总金额与账面勾稽无未说明丢失；每条异常可追溯到原始数据；程序失败时不输出误导性结论；最终结论由人签字批准。

进展与下一步

v0.1 流水线跑通 → v0.2 留痕补全（当前） → 真实数据平行运行 → 本地部署模型作为 AI 候选层（L1：只出候选、不出结论，用于扫描件识别、合同条款提取、客户名称模糊匹配、中英泰异常描述初稿，并标明 AI 生成、人工修改和最终批准人）→ 函证、勾稽、账龄、三单匹配。待决事项：合伙人批准、硬件与模型选型、与人工的平行评测。

商业化

沉淀下来的积木：审计规则引擎、质量闸门、模块设计卡、留痕规范和方法论手册。它们可以直接复制给中小会计师事务所，交付形态是“3 天审计 AI Bootcamp → 本地化部署 → 陪跑”，数据始终留在事务所自己的电脑上。

B某国企人事部门：不换系统、不让模型碰钱，在原有 SaaS 上长出人事 Agent一期已交付

背景与约束

员工规模较大，薪资核算长期依赖 Excel 加人工核对。HR 熟悉每一条薪资规则，却说不清规则之间的关系：什么时候触发调薪、什么时候该停发、什么时候需要重新核算。约束：已有的人事 SaaS 不愿替换；薪酬数据高度敏感，AI 不能直接看明细。

我的判断

瓶颈不是模型，是“部落知识”。第一步不是上 AI，而是把只存在于 HR 脑子里的隐性规则显性化：流程画清楚了，系统自然就能搭出来。

一期（已交付）

和 HR 反复访谈，把“说不清的关系”一条条画成流程图，落成核算流程，并配套操作手册，让同事能自己排查常见问题。薪资核算从依赖个人经验，变成有据可查、可复用的流程。

二期（方案设计中）

不替换原有系统，在 SaaS 之上加一层：原有人事 SaaS → 数据治理网关（字段分级、脱敏 token 化、权限继承、审计日志）→ 人事 Agent（意图识别后调用一期的薪资规则引擎、制度问答、异动监听）→ 人工审批门（HR 复核通过后才写回 SaaS，驳回留痕）。

三条原则：模型不算钱（金额计算只走一期的确定性规则）、最小可见、不越权（Agent 权限继承 SaaS 角色）。

怎么衡量

不算“省了多少工时”，而是算“HR 同时能处理多少异动单”。二期指标待平行运行后填入真实数据。

商业化

沉淀下来的积木：隐性规则访谈法、数据定级表、治理网关设计、AI 面试评估模块（可接入招聘节点）。适合规则多、数据敏感、不愿换系统的企业：国企、集团公司、连锁企业的人事和财务部门。

C教培学管：让一位学管老师照顾更多学生，把判断留给老师搭建中

背景与约束

学管要为每个学生诊断薄弱点、定规划、跟进度，人均能覆盖的学生有限。错题散在作业本和照片里，没有对齐到知识点；规划靠个人经验。学生是未成年人，画像和错题数据按最小必要原则收集与授权。

我的判断

AI 的价值不是替老师做判断，而是把“需要老师判断的学生”找出来。知识点体系是地基：错题、规划、知识地图都挂在同一套知识点上。

方案架构

学生画像 + 错题拍照 → 题目识别、错因归类、对齐知识点 → 规划 Agent 生成定制路径，每一步链接到知识点 → 学生知识地图（缺失、已复习一眼可见）→ 学管后台（进度看板、人工介入队列）。识别不确定、进度停滞的学生自动进入学管队列；老师的指导回写画像，下一轮规划随之调整。

Agent 岗位卡

职责：错题归因、生成定制规划。权限边界：只看画像与错题，不替老师做课程决定。升级给人：识别不确定、进度停滞。自主度 L2（AI 执行，人审核）。衡量指标：学管人均跟进学生数。

下一步与商业化

下一步是家长学情周报、课程与排课联动。这套“识别 → 规划 → 人工队列”的结构可以复制到K12 培优、语言培训、职业教育机构的学管和班主任岗位。

D制造业物流：一个岗位靠电话串起整条履约链，先拆清，再自动化诊断中

背景

E个体药店：技术难度不高，真正的工作量在确认人机分工已交付

背景

老板每天手写出入库记录，耗时且容易出错。没有技术背景，也从没想过流程可以被简化。

我的判断与做法

和老板一起梳理出入库场景，先判断“拍照记录”是否可行；再搭拍照即记录的小工具，照片自动识别商品名与数量，自动生成台账。技术难度不高，真正的工作量在反复确认哪些信息必须人工核对、整个流程怎么跑通。

交付与结果

交付的是工具 + 操作手册 + 教学视频，老板照着视频 3 分钟就能上手。每天花在出入库上的时间，从半小时降到几分钟。

2026.09从数字员工到数字组织：读完麦肯锡的七条 AI 真相，我给自己提了四个问题约 8 分钟
麦肯锡访谈了 15 家 AI 原生公司，总结出七条运营真相。我没打算一条条复述（报告写得比我清楚），而是把它和自己这两年驻场做 AI 落地的笔记摊在一起读。最后留下四个问题：增量在哪，SaaS 死没死，中层何去何从，个人靠什么不被取代。

01 数字员工会把组织变成什么样？

麦肯锡的第一条真相是：AI 不是工具，是队友。

报告里有个画面很具体。一家 A 轮公司的 CEO 有一整套私人 agent：一个回邮件、排日程；一个录会议，会后自动把下一步发给相关的人；一个盯着数据看板，实时给他分析。他说自己的产能翻了五倍。

还有更夸张的。一个顾问以前同时跟 50 单交易，现在能跑 3000 单。人没有多招 60 倍，多出来的量全是 agent 分析师在扛，人只负责那些高风险、要靠信任谈下来的关键对话。另一家 4 个人的可持续发展创业公司，同时服务 20 家企业客户，一份合规报告几分钟出完，以前律所要做好几周。

以前我们说"数字员工"，脑子里想的是用 AI 替掉某个岗位。但这些案例里发生的事不太一样：是一个人带着一支 agent 小队，去干以前一整个团队才干得了的活。这已经不是多了一个员工，而是多了一个"数字组织"。

（后面我说的 agent、数字员工，指的都是同一个东西，就是能自己接活、干活的 AI。）

这不是效率提升，这是另一种商业模式。

但让我卡住的，是麦肯锡提到的"结构性依赖"。交给 agent 的事越来越多，组织就会慢慢围着 agent 重建。人碰这些活的机会越来越少，经验和判断力一点点流失。等哪天 agent 出错，或者遇到它没见过的情况，已经没人接得住了。

一家农业科技公司的 CEO 问了一个我很喜欢的问题：我们把越来越多的事交给 agent，是不是正在制造一些自己还看不见的危机？

他们的解法不是少用 AI，而是刻意设计人的位置：把人放到 agent 真搞不定的地方，比如全新的科学判断、合作伙伴关系；同时给 agent 留好一条"搞不定就交回给人"的通道。

所以数字组织不是"人越来越少"，而是得想清楚，人到底该站在哪儿。

02 增量在哪？SaaS 死了吗？

这一节其实是我读的时候在笔记本上连着打的几个问号：增量到底怎么算？SaaS 还有没有未来？

先说增量。

我见过的很多老板，一提 AI 第一反应是降本，能不能少招两个人。这没错，但如果只停在这一步，AI 带来的就只是存量里的内卷：同样的客户、同样的单子，只是做得更便宜。

麦肯锡给了一个我觉得特别关键的标准：别再问 AI 帮你省了多少小时，要问有了 AI，你的业务现在敢试什么以前想都不敢想的事。

这点我自己深有体会。我现在给客户定指标，已经不算"省了多少时间"了，而是算"同样的人手，现在能多接住多少活"。前者的尽头是裁员，后者的尽头才是增长。（老板们一开始都更爱听前者，这个我理解。）

我的理解是：用 AI 去探索业务的边界，也在业务里探索 AI 的边界。

50 单到 3000 单，4 个人服务 20 家企业，这些才叫增量。对中小企业来说，与其让 agent 去替现有岗位，不如派它去做以前根本够不着的事：长尾客户、边缘市场、以前因为太费人而放弃的业务。

再说 SaaS。

报告里那位农业科技公司的首席战略官说了句很冲的话：SaaS 已死，集成一个工具花的时间，比自己造一个还长。有了 Claude Code、Cursor 这类工具，懂技术的团队几个小时就能搭出一个内部工具。

但麦肯锡自己在后面泼了盆冷水：造一个工具现在很便宜，养一个工具一点都不便宜。每个部门都自己搭一堆小工具，维护的账单迟早会来。

它给的判断标准挺清楚：

  • 能让你与众不同的东西，也就是基于你自己的数据、经验、知识产权的，自己做；
  • 其他的先买现成的，但有三条硬要求：AI 原生的接口、能和别的系统打通、能随时换掉。

所以我觉得，SaaS 没死，死的是"买一套大而全、把你锁死的系统"这种买法。以后的软件更像一块块积木，agent 随时能调用，不好用就拔掉换一块。麦肯锡管这叫"为替换而设计"：底下是很薄的一层治理（身份、权限、安全），上面插各家最好的工具，连模型都要能随时换。

我在笔记上画了一条路径：

降本增效（助手放大）→ 内部工具（自动执行）→ 增长引擎（业务增量）

大多数公司，还停在第一格。

03 中层怎么办？我的"1+1+1+3"

麦肯锡的第六条真相是：平台集中管，任务分散做。

意思是，没有哪个中央 AI 部门能一个人推动整个公司转型。一位负责 AI 运营的总监，一上来就跟自己说"我不是专家"，因为一个人不可能搞懂所有部门的业务。更好的做法是：技术团队把底座搭好、把安全管住，每个业务部门自己决定 AI 怎么用。

还有个数据挺扎心：员工说 AI 帮自己干了三成以上日常工作的比例，是老板以为的三倍。卡住规模化的往往不是员工不愿意用，而是领导放权太慢。

读到这里，我在笔记上写下了"1+1+1+3"：一个最小作战单元里，1 个高层、1 个中层、1 个员工，再加 3 个数字员工。

高层要先做一件事：给决策分类。

这里有个"杰文斯悖论"：一样东西变便宜了，大家反而会用得更多。决策也是这样。AI 把每次决策的成本打下来，要做的决策就会暴增。如果高层不先分清楚哪些交给流程和 agent、哪些必须自己拍板，最后只会被淹死在一堆"要不要"里。

中层要变成"内部 FDE"。

FDE 是 Forward Deployed Engineer，前线部署工程师，原本指那种驻扎在客户现场、懂业务、又能直接写代码交付的工程师（对，就是我平时在干的活）。放到公司内部，就是那个懂业务痛点、会调 agent、能直接把工作流搭出来的人。中层作为内部 FDE，负责定方向、定边界、担结果：哪些流程值得重做，哪里让 agent 自己跑，哪里必须留给人。

员工里也要有 FDE：一个人带三个数字员工，负责把东西搭出来、养下去，也负责把一线冒出来的新机会往上提。

两者都得会动手，区别只在于谁做决定、谁对结果负责。

这里要补一句麦肯锡的提醒，它和"1+1+1+3"是同一件事的另一面：信任先于自主。

报告里有个差点翻车的故事。一家公司让 AI 帮忙回合同邮件，AI 很快起草了一封"改动都没问题，就这么办"，但那些条款其实还得接着谈。好在发出去之前被人拦下了，他们立刻关掉了这个功能。还有一位创始人说得很实在：先手动做，做到痛得受不了再自动化，而且一步一步来。AI 最适合做中间，开头和结尾还得是人。

这条我在项目里是真的这么干的。之前给一家审计事务所做底稿自动化，我们的设计就是：模型部署在他们本地，AI 只给候选结果，人来确认。我把 agent 的自主程度分成 L0 到 L3 四级，一开始只让它待在最低的那一级跑，跑稳了、大家信它了，再往上放。

所以内部 FDE 不只是会搭，更重要的是知道哪里不能让 agent 自己做主。

04 个人靠什么不被取代？

麦肯锡的第三条真相，是我读完觉得最实在的一条：瓶颈不在模型，而在于能不能调得动你的"部落知识"。

部落知识，就是那些只存在于人脑子里、从来没写下来的经验。你问 agent 一个问题它答不上来，很多时候不是模型不够聪明，而是答案根本没被记下来，或者放在它够不着的地方。有位受访者说：这不是 AI 问题，是知识管理问题，AI 只是把它暴露了出来。

所以我越来越觉得，未来手里无形资产、知识资产越多的人，越不容易被 AI 取代。

能写成流程的工作，比如整理纪要、做标准表格、写模板化回复，正在快速贬值，因为 agent 学得会。但那些写不成流程的东西，比如对一个行业的判断、和客户之间的信任、面对复杂局面时的直觉，才是护城河。

不过光有积累还不够。麦肯锡建议企业把会议全录下来、自动转写、放进共享知识层。放到个人身上也一样：你得学会把自己的经验整理好，"喂"给 agent。知识资产越厚、越有条理，AI 在你手里的杠杆就越大。

这也是我自己在做的事。

我有一个四千多个文件的个人知识库。第一版是 7 月搭的 RAG，一次性把所有资料提取进去，刚做好的时候真的很好用，问什么都能翻出来。后来我才意识到，它只是一张快照：之后我改过的方案、推翻的判断，它全不知道，却会用一模一样笃定的语气，把两个月前的旧结论当成答案递给我。

这就是报告里说的"知识腐烂"。可怕的不是资料旧了，而是 AI 不会告诉你它旧了。

所以 9 月我重新搭了一套。不再追求一次塞满，而是让它自己能动起来：按项目、领域、资源、归档分层；写了个脚本自动扫描全库、重建索引；每周一定时跑一次，哪些东西放太久没更新，它会直接点名。（比如我的增长实验日志超过七天没动，它就会提醒我。被自己搭的系统催更，体验挺微妙的。）

我现在觉得，知识库不是仓库，而是一个需要新陈代谢的系统。

最后想留一点怀疑。

15 家公司，样本不大；而且都是已经做成了的 AI 原生公司，天然偏乐观；受访者大多是高管，讲的也多是正面经验；这篇报告本身也在推麦肯锡自己的方法论。所以我把它当成一份很好的清单，而不是定律。

但有两句话，我会一直记着。

一句是麦肯锡的：别问 AI 帮你省了多少钱，要问有了 AI，你的团队现在敢尝试什么。

另一句是那位农业科技 CEO 的，大意是：人机协作的重点不在用 AI 替代人，而在精准地找到人不可替代的地方。

对组织来说，这是在找人该站的位置。

对我们每个人来说，这是在问自己：我那份写不成流程的东西，到底是什么？

2026.09序安 Process Sentinel：重工业场景的 AI 可行性研究方法论约 4 分钟

为什么高风险行业需要不一样的方法论

前面几篇案例文章里的场景——药店、国企 HR、企业审批——共同点是错了可以改、慢一点也没关系。但重工业、能源这类场景不一样：一次误判可能是安全事故，一次错误的自动化决策可能牵扯到环保合规甚至政策红线。

序安（Process Sentinel）是一个面向重工业高风险场景的 AI 应用可行性研究与原型验证项目，研究对象是贵阳息烽磷煤化工园区——一个磷、煤、电、固废深度耦合的复杂工业系统。这个案例展示的不是"我们上了什么模型"，而是在高风险、高监管行业里做方案该有的方法论：先把一手资料查扎实，再谈技术怎么落地。

研究方法：先查证，再设计

这类项目最容易犯的错误，是拿着一套通用的"AI+工业"话术直接套上去，缺乏对具体工艺流程和监管背景的扎实理解。序安的方案基于一批可核查的一手资料——园区总体规划环评报告书、贵阳市生态环境局的公开通报、贵州省的政策文件（黔府发〔2024〕5 号）、公开发表的技术文献——完整梳理了工艺流程与物料流向，而不是从二手资料或通用行业知识出发拍脑袋。

这一步看起来"不够技术"，却是整个方案能不能落地的前提——脱离真实工艺流程和真实监管约束谈 AI 应用，做出来的方案大概率是空中楼阁。

识别出的三处现实短板

基于扎实的资料梳理，研究识别出园区当前存在的三处现实短板：

现实短板具体表现
质量指标滞后湿法磷酸、磷酸铁等工段的关键质量指标依赖人工离线化验，与实际工况存在时间差，异常征兆难以提前识别
渣库风险事后发现磷石膏渣库渗滤液风险长期是"泄漏后才监测到"的事后模式，2017 年环保督查、2023 年官方通报均指向同一短板，缺少 7×24 小时前置预警能力
"以渣定产"推演不足生产规模受磷石膏消纳能力政策约束（黔府发〔2024〕5 号），但多装置联动推演依赖人工 Excel 物料衡算，效率不足

三个短板的共性是：都不是"没有数据"的问题，而是"数据没有被及时用起来"的问题——化验数据存在，但滞后；渣库有监测，但是事后的；物料衡算能算，但靠人工 Excel，跟不上多装置联动的复杂度。这正是 AI 系统能补的位置。

方案定位：只读辅助，不接管生产

在高监管、高风险场景里，方案设计上最重要的一条原则，是明确边界：提出的 AI 系统严格只读采集 DCS 与传感器数据，不向生产控制系统下发任何指令，不接管生产。预测、预警、仿真结果，只作为工艺工程师与操作人员的参考建议，而不是自动执行的决策。

这不是技术上的保守，而是这类场景应有的责任边界——生产控制系统的自动化决策一旦出错，后果不是"重新跑一次"能解决的。

实施路径按风险从低到高分三个阶段：

  1. 阶段一：离线验证——仅用归档历史数据训练，不接触现场系统，风险最低。
  2. 阶段二：在线只读测试——本方案建议的重点阶段，系统只输出结果，不写回任何控制指令。
  3. 阶段三：人工辅助建议——远期阶段，不建议在当前阶段开展自动闭环。

这种分阶段推进本身就是方法论的一部分：不是因为技术做不到闭环，而是在没有充分验证之前，闭环的风险大于收益。

原型进展：说清楚"是什么"和"不是什么"

六个应用场景里，已经做成可运行原型的有两个：

  • 交椅山磷石膏渣库渗滤液早期预警：用 180 天合成示意时序数据验证"先导指标能否早于污染物超标提前预警"这一假设，一次固定随机种子的结果是提前 44 天预警。
  • "以渣定产"园区物料平衡仿真：按消纳上限推演多装置可行负荷组合，把原本靠人工 Excel 完成的联动推演自动化。

化工行业的DCS系统承担生产控制与安全联锁，任何第三方系统只允许只读获取数据，不允许向DCS下发写控制指令。

所以我们的判断很明确：“AI接管生产”在化工行业不成立。能做的是在DCS之外搭建一套辅助系统——只读采集数据，做预测、预警、仿真，结果供工艺人员参考，不自动调节任何阀门。

开场：认识和方法之间，差一个"怎么做"

如果你已经读懂了上篇的认知——翻译比使用重要、设计比操作重要、赋能比替代重要——那接下来的问题是：

具体怎么干？

这篇给你一套完整可执行的方法。它不是理论，是我做了药店出入库、国企人事系统、保密数据系统、多智能体协作这些项目后，沉淀下来的固定打法。照着走，至少能让这件事"知道第一步做什么"。

一套可复制的工作方法

我做每一个项目，基本都走同样的五步：

步骤动作需要的能力
1. 跟岗观察去看同事每天在忙什么、卡在哪、重复什么业务敏感度
2. 痛点定位找到那个"繁琐、高频、易错"的环节抽象能力
3. 流程拆解把模糊的"记单子"拆成"拍照→识别→填表"逻辑拆解力
4. 翻译封装拆成AI动作链 + 写触发规则 + 写操作文档翻译能力（最核心）
5. 赋能输出教会同事 + 形成案例 + 对外分享传播与复制能力

下面逐步拆开讲。

第1步：跟岗观察——先别急着谈AI

很多项目一上来就聊工具、聊AI能干什么。这是错的。

正确的做法是先闭嘴，去看。坐在同事旁边，看他们每天到底在忙什么、卡在哪、哪些事反复在做。AI介入的前提，是你先真的搞懂这份工作。

第2步：痛点定位——找到那件"繁琐、高频、易错"的事

不是所有环节都值得上AI。真正值得做的，是同时满足三个特征的事：

  • 繁琐：步骤多、重复、机械；
  • 高频：每天都在发生，而不是一年几次；
  • 易错：靠人容易漏、容易错。

药店老板的出入库符合这三条；国企的薪资核算符合这三条。找到这样的环节，AI的价值才是实的。

第3步：流程拆解——把模糊的"记单子"拆成清晰的步骤

客户描述工作时是模糊的——"我就是记单子"。你不能拿这句话去配AI，得把它拆开：

"记单子" → 拍照 → 识别商品 → 填数量 → 生成台账 → 人工核对 → 归档

拆到这一步，AI插在哪、人做什么、哪些能自动化，一目了然。这一步最考验逻辑拆解力，也是后面所有工作的地基。

第4步：翻译封装——整篇方法的核心

这是我说的"翻译"真正落地的地方。把拆好的流程，翻成三样东西：

  1. AI动作链：每一步AI具体做什么、输入输出是什么；
  2. 触发规则：什么情况启动、什么情况停止、什么情况回退；
  3. 操作文档：员工照着就能用的指南，不用动脑。

这一步最难复制、也最值钱。前面的观察、定位、拆解，都是为它做铺垫；后面的赋能，只是把它交付出去。

第5步：赋能输出——让同事真的用起来

系统做完了，员工不会用，等于白做。

不是开一场培训会就完事，而是先找3-5个"种子用户"——业务熟练、对新工具有好奇心的人——手把手教会。等他们用出效果，再由他们带动其他人。

培训不是教功能，是教"什么时候该想到用AI"。功能会忘，但思维方式不会。

怎么找到适合自己企业的第一个场景

回到最开始的问题：企业不知道从哪里开始。

我的经验是，与其想清楚再动手，不如先找一个足够痛的场景，快速跑起来，看到效果之后自然知道下一步。

适合第一批落地的场景，通常同时满足三个条件：

  1. 业务痛点足够疼：员工主动提需求，而不是领导强推。
  2. 数据基础过得去：不需要大动干戈做数据清洗，现有资料和流程已经可以支撑。
  3. 风险边界清晰：即使出错，也在可控范围内，有人能兜底。

按这三个条件过滤，我从上百个场景中筛出了几个优先级最高的：

场景一：知识问答

企业制度、产品资料、技术文档分散在各个角落，员工遇到问题时，查找耗时，还难以判断资料是否准确、是否为最新版本。

做法：不是推荐一套知识库系统，而是先和客户一起梳理——哪些文档是最常用的、哪些问题是被问得最多的。然后用最简单的方式搭起来，跑起来，再迭代。

场景二：采购信息汇总

采购人员寻找新供应商时，需要在多个平台反复搜索，耗费时间，也容易错过更合适的供应资源。

做法：不是上一个智能采购系统，而是先帮采购人员梳理：他们现在怎么找供应商、哪些步骤最费时间、有哪些信息是可以自动汇总的。从一个具体的小环节切入，而不是整体替换。

场景三：合同审查

合同量大、条款复杂，人工审查耗时且容易遗漏风险。

做法：不是上一个AI法务平台，而是先帮法务人员梳理：他们最怕哪种类型的风险、最常审哪种类型的合同、审一份合同最费时间的环节在哪里。从最痛的那个点开始。

场景四：财务发票核对

财务人员需要人工识别发票内容、核对报销单据，工作重复、数据量大，容易积压和差错。

做法：不是上一个RPA系统，而是先和财务一起梳理：发票核对的完整流程是什么、哪些步骤是机械重复的、哪些环节需要人工判断。从机械重复的那几步开始。

评分较高的场景进入第一批建设；价值高但数据条件不足的场景，可以先做流程梳理；价值低、实施难度又高的场景，暂缓。

工具只是手段

Codex、Claude、WorkBuddy、还有我们自研的多智能体执行系统ForgeOne——这些是我日常使用的工具链。但工具不是重点。同样的场景，换一套工具也能做。 真正不能替换的，是蹲在现场看客户怎么干活的那个过程。

不同工具适合不同的环节：

  • 需要快速出原型，用Codex或Claude直接生成；
  • 需要改造工作流，用WorkBuddy做流程编排；
  • 需要多个环节串联执行，用ForgeOne做多智能体协作；
  • 涉及保密数据，AI辅助搭建、数据不出网。

工具选型的依据不是哪个更先进，而是哪个更匹配当下的业务约束。

一个真实困境

"我们研究AI半年了，领导也很重视，但就是不知道从哪里开始。"

这是过去两年我在和各种企业打交道时，听到最多的一句话。

企业面临的不是技术焦虑，是决策焦虑——信息太多、场景太多、选择太多，反而不知道先做什么。我见过太多企业花几个月做调研、写PPT、开评审会，最后一个场景都没落地。

真正的难题不是"AI能做什么"，而是"我该从哪里开始做"。

而在回答这个问题之前，我想先讲几段真实的经历。它们共同指向一个结论：AI落地的第一道坎，从来不是技术。

我帮他们做了什么

过去一段时间，我在做一件具体的事：驻扎在客户现场，帮他们从日常工作中找到可以用AI提效的环节，然后真正落地到使用。

以下是几个真实的案例。

案例一：药店老板的出入库

一位药店老板，每天花大量时间手写出入库记录。我问他：能不能拍照？他眼睛一亮：可以。

于是我给他做了一个工具——拍照就能记录，照片自动识别商品名和数量，自动生成台账。他现在每天花在出入库上的时间，从半小时降到了几分钟。

技术难度：极低。但我花了很长时间和他一起梳理：哪些环节可以合并，哪些信息必须人工确认，整个流程怎么跑通。

案例二：国企人事薪资管理系统

一家国企，员工很多，薪资核算靠Excel表格+人工核对。HR同事对每一条薪资规则都清楚，但说不清规则之间的关系——什么时候触发调薪、什么时候该停发、什么时候需要重新核算。

我和她一起，把这些"说不清的关系"一条一条画了出来。画完之后，系统就自然长出来了。

技术难度：中等。但最大的工作量，是和她反复沟通，把她脑子里的隐性逻辑显性化。

案例三：配套的操作手册和视频教程

系统做完之后，我发现光有系统还不够——使用者的习惯不会自动改变。

于是我给每个系统都配套了操作手册和使用视频。药店老板照着视频，三分钟学会；国企同事拿着手册，可以自主排查常见问题。

交付物不是一份PPT，是一套有人用的系统。

案例四：涉及核心保密数据的系统搭建

有一类企业数据——员工薪酬明细、核心配方、经营利润——碰都不能碰公网。

我的做法是：用AI辅助搭建一套内部系统，数据全程不出局域网。AI负责写代码、搭架构、调逻辑，人负责定义规则和验收结果。最终交付的是一个跑在内网的独立系统，既能用AI的能力，又不触碰数据安全红线。

技术难度：中高。关键不是能不能做，而是搞清楚"哪些事交给AI，哪些事必须人来把控"。

案例五：多智能体协作处理复杂任务

有些业务不是单一工具能解决的——比如一个审批流程涉及数据提取、规则校验、风险预警、报告生成四个环节，每个环节的输入输出都不同。

我用自研的多智能体执行系统（ForgeOne），把每个环节交给一个专门的"智能体"处理，它们之间自动传递数据、协同工作。人只需要定义每个环节的规则，系统自己跑通整条链路。

技术难度：高。但核心工作量不在写代码，在于拆解业务：每个环节的输入是什么、输出该交给谁、异常怎么回退。

案例六：AI无法替代的人工环节

不是所有工作都适合用AI。有些环节必须人来做——面对面沟通、需要判断力的决策、涉及信任关系的场景。

我的做法是：把AI能做的全部自动化，剩下必须人做的部分，设计成标准化的工作流。每一步谁做、做什么、做完交给谁，流程图上画得清清楚楚。

技术难度：低。但价值极高——员工终于知道自己该干什么、什么时候干、干完交给谁。

案例七：培训核心员工用AI提质增效

系统做完了，员工不会用，等于白做。

我的做法不是开一场培训会就完了，而是先找到3-5个"种子用户"——他们本身业务熟练、对新工具有好奇心——手把手教他们用AI处理日常工作。等他们用出效果了，再由他们去带动其他人。

关键心得：培训不是教功能，是教"什么时候该想到用AI"。功能会忘，但思维方式不会。

落地的真实难点

做完这些案例之后，我对"AI落地难"这件事有了不一样的理解。

很多人以为难点在于：不知道怎么用AI、哪个AI工具更好、Prompt怎么写。

但真正卡住的环节，从来不是这些。

难点一：从工作中找到可以用AI提效的环节

客户知道自己在做什么，但说不清哪些环节可以合并、可以省略、可以自动化。

药店老板知道出入库怎么记，但从来没想过"拍照就能记"这件事。国企HR知道薪资怎么算，但从来没梳理过"人员流转"和"薪资核算"之间的触发关系。

帮她画清楚工作地图，才是真正的价值。

难点二：真正落地到使用

做一个能跑通的概念验证不难，但让人真正用起来、用得顺手、出了问题知道怎么处理——这才是挑战。

使用者的习惯不会自动改变。系统上线≠落地成功。

难点三：沟通成本和环节设计

每个客户的业务流程都是独一无二的。标准化的SaaS解决不了的问题，往往在于环节之间的逻辑关联。

一件事触发另一件事，另一件事的结果又影响第三件事——这种事务之间的关联，才是设计的核心。

三个核心认知

做了这么多案例之后，我提炼出三个认知。它们是我做这件事的底层逻辑，也解释了为什么"教人用AI"这条路走不通。

认知一："翻译"比"使用"重要

大部分企业培训AI，是在教员工学AI的语法——怎么提问、怎么描述需求、怎么写Prompt。

但我做的正好相反：不是让人学会AI的语言，而是让AI学会业务的语言。

把"记出入库"翻译成"拍照→识别→生成台账"，把"算薪资"翻译成"人员变动→触发调薪→重新核算"。AI听得懂的不是业务，是我翻译过去的动作链。

所以问题的关键从来不在于员工"会不会问"，而在于有没有人把业务翻译成AI能执行的东西。

认知二："设计"比"操作"重要

企业里不缺会点按钮的人，缺的是能设计"别人怎么点按钮"的人。

当你把业务拆成流程、把流程配成规则、把规则封装成员工不用动脑就能照做的指南——员工不再是操作员，而是流程的受益者。他们不需要记住每一件事怎么做，只需要按照设计好的工作流执行。

做AI落地，我卖的不是工具，是"别人怎么用工具"这件事的设计。

认知三："赋能"比"替代"重要

很多人担心AI会取代员工——这不是我的视角。

我做的是让AI把重复、繁琐、易错的部分吃掉，把员工从"这玩意儿怎么用"的困惑里解放出来，去做那些AI做不了的事。员工没有被替代，他们只是不再需要做机器擅长的事。

AI进企业，替代的从来不是人，是重复劳动。

上篇小结

看完这些案例和三个认知，你应该理解了我为什么说"AI落地的第一道坎不是技术"。

工具随时在变，案例各有不同，但底层的那件事始终没变：有没有人能把业务翻译成AI能执行的工作流。
